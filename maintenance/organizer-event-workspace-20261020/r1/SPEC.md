## Три входа и переходы

- Кабинет: ?case=K01, live ?case=K03. Назад → связанная копия принятого списка; карточка/«Открыть» → кабинет выбранной записи; «Править» → редактор этой записи. Из кабинета → редактор; сохранение → обновлённый кабинет; назад → список с теми же локальными данными/вкладкой. Адаптер восстанавливает прокрутку; точная пиксельная приёмка её восстановления не заявляется.
- Редактор: ?case=E02. Начальные поля отражают текущее событие. Правки/афиша/статус меняются только в памяти этого iframe. Успех показывает фактический результат симулятора; обычные правки сохраняют pending/removed, отправка на проверку — отдельное действие. Снятие с афиши требует подтверждения и не означает отмену/возврат.
- Архив: ?case=A01, отмена ?case=A02. Тот же кабинет с общей структурой, без «Пришли», редактирования, сканера, обратного отсчёта, удаления или перепубликации. Старый прямой editor вход A08 показывает блокировку и возврат к просмотру.
- Гости/сканер/публичная афиша/вход и соседние разделы списка — явные границы в наружной панели. Эти дочерние страницы не перепроектированы и не имитируют серверный успех.

## Сохранение и безопасные границы концепта

Общий save отключён без изменений и во время операции. Поля остаются в форме при ошибке. Неизвестный ответ блокирует повторную отправку до отдельного «Проверить результат»; показаны обе ветки readback (сохранено/не сохранено). Конфликт предлагает остаться или явно загрузить актуальную версию с предупреждением о замене правок. Запоздалый ответ относится только к своей операции; действия закрываются после архивирования/потери доступа.

Выход по заголовку/«Отмена»/браузерному Back при dirty вызывает подтверждение. Учитываются и несохранённые лимиты, а не только сведения. beforeunload предусмотрен для закрытия/перезагрузки; физическая проверка закрытия окна/native не выполнялась. Наружный переключатель сценариев намеренно сбрасывает демонстрацию через отдельный reset handshake.

Лимит сохраняется отдельно. Отмена сведений не откатывает уже сохранённый лимит. Если общий save прошёл, а лимит ещё не сохранён, редактор остаётся открытым с точным пояснением. Общий save и quota-save не запускаются одновременно. При завершении события ответ квоты не выдаётся за успешную новую запись. Конкретная серверная атомарность/конкурентность не доказана этим UI.

Афиша выбирается из локального демонстрационного набора, с отменой/возвратом прежней; реального image-picker/Storage upload/delete нет. Для выбора, upload-error, access-denied, invalid-file предусмотрены состояния. Симулятор операций в наружной панели задаёт success/pending/error/upload-error/unknown/conflict/access/archive; это не серверные ответы. Состояние in-flight можно явно завершить наружной кнопкой. Нет fetch/API/auth mutations, localStorage/sessionStorage, реальных заказов, платежей, писем, сканов или сохранения чужих данных.

Денежные значения — копейки; копейки не округляются, unknown ≠ zero, ticket revenue ≠ payout. Для очень большой суммы блок расширяется, цифры не обрезаются. Бесплатное событие и смешанные типы различаются. Конкретное значение выручки/возврата не подтверждено банковской операцией.

## Открытые вопросы интеграции

1. Исходный hasEnded использует start+6h без end. Принятый список и этот прототип сохраняют explicit unknown, а serverArchived в фикстурах — отдельный авторитетный признак. Перед интеграцией согласовать с фактическим серверным закрытием продаж, без тихого изменения правил или принятого снимка.
2. Сохранение полей/статуса, повторная модерация после существенных правок, публикация из removed и доступ во время события требуют сверки актуальных политик. Демонстрация не предоставляет новых прав и не доказывает серверный запрет обхода.
3. Перенос даты/места после продаж показывает подтверждение последствий. Автоматическая рассылка, возврат или отмена не обещаются; их политика и реализация отдельные.
4. Версии и неизвестный результат в прототипе контролируются в памяти. Нужны реальные readback/versioning/idempotency и проверка после reload в рабочем клиенте; fixtures это не заменяют.
